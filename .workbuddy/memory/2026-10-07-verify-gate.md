# 2026-10-07（第四轮）—— 用户纠正根因，改用验证闸门

## 用户纠正（我前两轮都错了）

我误以为「议价后必弹『确定捐赠这些物品？』框」，于是加弹窗自动处理 + 点「否」。
用户指出真实机制：

> 点「平衡报价」后会自动添加合适金额，再点「议价」，**不会弹出任何弹窗，
> 就是正确完成交易**。如果弹出这个框，**说明点击「平衡报价」失败了**。
> 平时我自己操作就是「平衡报价」→「议价」循环，根本不会弹窗。
> **但如果点击速度太快，可能会触发弹窗。**

### 正确的因果链
```
点太快 → 「平衡报价」点击被游戏吞掉 → 报价栏仍为空
       → 照点「议价」→ 游戏发现这单什么都没有 → 弹「确定捐赠这些物品？」白送框
```
**弹窗是失败告警，不是正常流程。**

我上一轮的错误在于：把弹窗当正常流程、还点「否」取消 → 等于把**失败固化成永久失败**
（每次都取消，交易永远完不成）。用户说「最初版本理解是对的，但没处理好」——
即间隔方向对，但缺少「验证」这一环。

## 本轮修复：验证闸门（核心）

不猜间隔、不事后收拾，而是**用「报价栏是否填入」作为唯一真值**：

1. 点「平衡报价」
2. `wait_price_filled()` 轮询报价区，检测是否出现内容
3. **未填入 = 点击被吞** → 退避 `retry_backoff_ms` 后重试，**绝不点议价**
4. 验证通过才点议价 → 正常完成交易
5. 保险：若仍弹窗，关掉并记为失败，下轮退避

另加：`max_balance_retries`(6) 上限保护、`balance_clicks/balance_fail` 统计，
进度行输出「平衡报价成功 N/M (xx%)」直接反映健康度。

## 判据选型：两次踩坑

### 坑1：平均亮度 → 判别窗口极窄
数字只占 ROI 极小比例，平均亮度被暗背景稀释。
实测：空=8.2，填入=13.7，**分离度仅 5.5**，阈值窗口 10~14，极不稳定。
（而且我最初设的 `price_filled_luma=12.0` 是**凭空猜的**，
 单元测试立刻暴露：合成底图亮度 20 > 12 → 空栏被判为「已填入」→ FAIL）

### 坑2 → 最终方案：亮像素占比
改用 `((gray > 90).mean())` —— 对「内容占多少」不敏感。
实测：**0% → 3.3%** 的绝对二分，阈值 1%~3% 都 PASS，判别窗口宽。
注意：占比会随 ROI 变大而稀释（4倍大 ROI → 0.29%），所以 **ROI 要框紧凑**。

新增 `calibrate_price_threshold()`：抓当前帧算出占比，取其一半作阈值，
随实际画面自适应，不依赖硬编码。

## 我犯的另一个错误：靠截图猜坐标

试图从截图反推 `price_roi` 坐标，错了 4~5 次：
- 扫描 y1920~1940 找到「亮像素占比 20%」→ 裁剪出来却是**「平衡报价」按钮**
- 用饱和度找彩色物品图标 → 找到背包里的物品，不是报价栏
- 坐标换算反复错（crop 尺寸 2040x1760 与显示缩放不一致）

**教训：不要靠视觉估算猜坐标。** 已有 `calibrate.py --price` 交互框选 +
自动标定阈值，比猜可靠得多。已把之前那个拍脑袋的 `guess_price_roi()`（偏移量
`ay-160` 是瞎猜的，实测证明错）**删掉**，改成带详细图文引导的手动框选。

## 配置调整（降低被吞概率）

| 项 | 值 | 原因 |
|---|---|---|
| `min_click_gap_ms` | 400 | 间隔加大，降低被吞概率 |
| `skip_move_below_px` | **0** | 关闭「近距离瞬移」，恢复完整贝塞尔移动 |
| `pre_click_delay_ms` | [20,45] | 点击前停顿加大（原 [5,15]） |
| `move_duration_ms` | [40,90] | 移动更慢更拟人 |
| `round_delay_ms` | [80,160] | 轮次间隔加大 |
| 新增 | `price_roi` / `price_filled_ratio` / `max_balance_retries` / `retry_backoff_ms` | 验证闸门 |
