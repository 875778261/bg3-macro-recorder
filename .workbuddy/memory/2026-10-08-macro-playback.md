# 2026-10-08 —— 新增 macro.py：录制回放方案（快 5 倍）

## 用户反馈

> 当前使用的是图像识别方案吗？感觉当前处理的速度特别慢，远远不如手动点击快。
> 你是否可以**直接录制我的鼠标动作**，然后需要的时候直接播放呢？

两个问题：确认是否图像识别、要求录制回放。

## 回答与结论

**1. 是的，此前是纯图像识别**（每轮全屏截图 + 模板匹配）。
**2. 用户判断正确 —— 图像识别在这里是过度设计。**

慢的真正原因（实测拆解）：

| 环节 | 耗时 |
|---|---|
| 全屏抓帧 3840x2160 | 69~88 ms |
| 模板定位两个按钮 | ~30 ms |
| **两次点击间隔（我设的 400ms）** | **800 ms** |
| 各种延迟 | ~200 ms |
| **单轮** | **~1100 ms = 0.9 轮/秒** |

关键洞察：**这两个按钮位置固定、面板不动，视觉识别只在「首次定位」有价值，
之后纯属浪费。** 而为了防「点太快被吞」设的 400ms 间隔（两击=800ms）反而
成了最大瓶颈 —— 那是我自己引入的。

## 新增 macro.py（混合方案，非盲放）

**不是纯盲放** —— 保留安全机制，只把「全屏模板匹配」换成「60x60 小块采样」：

1. `record`：F9 切换录制，捕获你的鼠标坐标 + 时序，
   自动提取「平衡报价 → 议价」这一对（判据：x 差 <400、y 增大、间隔 100~5000ms），
   存到 `macro.json`
2. `play`：直接回放坐标，但仍做三重保护
   - 金色判据检查平衡报价可点（60x60 采样，8ms）
   - 报价区验证是否真的填入（你已配置 `price_roi=[1718,367,403,247]`）
   - 白送弹窗兜底

### 性能（实测 mock 验证）

| 方案 | 单轮 | 速度 |
|---|---|---|
| 图像识别 `auto_bid.py` | ~1100 ms | 0.9 轮/秒 |
| **录制回放 `macro.py play --gap 150`** | **201 ms** | **4.98 轮/秒** |

**快 5.5 倍**。`--gap 100` 可达 6.7 轮/秒，`--gap 200` 为 4.0 轮/秒。

## 抓帧性能关键数据

```
全屏 3840x2160 : 69.2 ms/次
小块 60x60     :  8.2 ms/次   -> 快 8 倍
```

## 本轮修的 bug

1. `core.human_click` 加 `throttle: bool = True` 参数 ——
   回放时用 `throttle=False`（由 `--gap` 统一控节奏），
   否则会被 `min_click_gap_ms=400` 再阻塞一次，优势全无。
2. `macro.py` 里 `sw, sh = scr.size` —— `Screen.size` 是 **@property**，
   原写成当方法用会 `TypeError: cannot unpack non-iterable method object`。
   这是真 bug，不是测试问题。
3. 报价区越界裁剪：`min(w, sw - rx)` 可能为负，加 `max(1, ...)` 保护。
4. 删掉 `macro.json` 不存在时的 `input()` —— 无交互环境会 `EOFError` 崩溃。

## 踩到的坑

用 bash 单行 python 更新 README 时，**反引号被 bash 解释**，
文档里的 `auto_bid.py` 等命令被实际执行，输出（`[错误] 找不到 macro.json`）
被写进 README 污染。
**教训：修改含反引号的 Markdown 必须用 Edit 工具，不能用 bash 内联脚本。**
