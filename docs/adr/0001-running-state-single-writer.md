# 运行状态由 `_end_session()` 唯一改写

**背景**：回放线程有多条退出路径（用户停止、角落急停、异常、循环自然结束），
原先只有「用户主动停止」会复位运行状态 —— 其它路径退出后 `_running` 仍为 True、
托盘仍显示「运行中」，于是下一次「开始」被静默忽略（粘滞状态）。
用户报告的现象正是「甩到左上角停了之后再也起不来，必须先右键停止」。

**决定**：`launcher.py` 里只有两个函数能改写运行状态 —— `_begin_session()`
（已停止 → 运行中）与 `_end_session()`（运行中 → 已停止）。回放线程把自己的
退出原因交给 `finally` 里的 `_end_session()`；`stop_playback()` 只负责发停止信号
和等线程收尾，不再自己改状态。`_end_session()` 幂等，所以「线程收口」与
「调用方兜底收口」可以同时存在而不会互相覆盖。

**考虑过的替代方案**：
- (A) 回放线程自持生命周期（在 `finally` 里自己改 `_running`、自己刷托盘）——
  能修掉本次 bug，但「状态改写」仍散落在调用方与线程两处，下次再加退出路径
  一样会漏。这正是本次故障的成因，只是换了个地方。
- (B) launcher 起看门狗线程轮询回放线程是否存活 —— 与回放逻辑解耦，但引入
  第二条时序，且「为什么结束的」这一信息在轮询里已经丢了。

**后果**：所有退出路径都必须经过 `_end_session()`，漏调用的后果从「状态永久
卡住」降级为「状态晚一步复位」—— 因为 `start_playback()` 还会自愈：
发现 `_running` 为真但线程已死时，先补一次收口再启动。托盘菜单文字与图标
同样只在这两个函数里同步，不再有别的地方碰它们。
